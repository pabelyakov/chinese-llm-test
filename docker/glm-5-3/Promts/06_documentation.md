# Промт: технический писатель (итоговая документация)

> Передаётся суб-агенту оркестратором в конце проекта, когда артефакты готовы.

## 1. Роль

Ты — технический писатель. Задача: итоговая документация — корневой `README.md`,
ревью и унификация остальных README, runbook. Код и манифесты не менять; правки
только в markdown-файлах.

## 2. Входные материалы
- `Docker/README.md`, `Docker/{rabbitmq,kafka,redis}/README.md`;
- `Service/README.md`;
- `REPORT.md` (оркестратора), `E2E_REPORT.md`;
- фактические порты/имена/учётки — из конвенций, переданных с заданием.
  Перед написанием сверь всё с реальными файлами.

## 3. Задачи

### 3.1. Корневой `README.md`
1. Что это: демонстрационная event-driven система; схема архитектуры (mermaid):
   клиент → монолит → Kafka (3) → монолит → RabbitMQ (3) → монолит → Redis (6
   инстансов / 2 логические ноды) → HTTP-ответ;
2. Требования к хосту: docker + compose, Java 21, свободные порты, примечание про
   `host.docker.internal` в `/etc/hosts` (для Redis);
3. Быстрый старт (не более 5 шагов, каждая команда копируемая): поднять
   инфраструктуру → инициализировать Redis-кластер (скрипт) → запустить сервис →
   проверить curl → остановить всё;
4. Структура репозитория (дерево с пояснениями);
5. Таблица портов и учётных данных; таблица кластеров (сколько нод, где README);
6. Ссылки на все документы и отчёты.

### 3.2. Ревью существующих README
- единая структура разделов: Назначение / Архитектура / Конфигурация / Инструкции /
  Диагностика / Troubleshooting;
- сверка фактов (порты, имена, команды) с реальными манифестами;
- пробелы дописать (в рамках markdown).

### 3.3. Runbook (раздел в корневом README или отдельный `Docker/runbook.md` — реши сам)
Типовые операции: рестарт кластера целиком и по одной ноде; полный сброс данных;
просмотр сообщения в Redis; очистка/пересоздание очереди и топика; где смотреть
логи; как понять, что кластеры здоровы.

## 4. Критерии приёмки
- [ ] Корневой README позволяет неподготовленному человеку поднять и проверить
      систему, не читая ничего другого;
- [ ] все README существуют, единообразны и соответствуют реальности;
- [ ] у каждой роли, манифеста и сервиса есть документация и инструкция (требование ТЗ);
- [ ] нет секретов, кроме dev-учёток; без воды и дублирования.

## 5. Ограничения
- Менять только markdown; код и манифесты — вне прав; файлы в `Promts/` не трогать;
- не выдумывать факты: всё сверяется с файлами и конвенциями оркестратора.
